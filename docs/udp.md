# UDP 概念文档

> 配套实验：`udp/echo`、`udp/retry`，抓包现场见 [packet/udp.md](../packet/udp.md)。

## UDP 是什么、在哪一层

UDP（User Datagram Protocol）与 TCP 同属**传输层**，但它只做一件事：**在 IP 之上加一个端口号**，让"哪台机器上的哪个进程"能收到数据。其余一切——连接、可靠、有序、流控——全部不存在。

```text
TCP 报文头：20~60 字节（SEQ/ACK/窗口/选项...）
UDP 报文头： 8 字节，只有 4 个字段：
  Source Port | Destination Port | Length | Checksum
```

## 核心语义对比

| | TCP | UDP |
|---|---|---|
| 连接 | 三次握手建立状态 | **无连接**，拿起就发 |
| 边界 | 字节流，无消息边界 | **数据报（datagram），一次发送 = 一个完整报文** |
| 可靠 | SEQ/ACK + 重传保证不丢不重 | 尽力而为（best-effort），可能丢、可能重复 |
| 有序 | 保证顺序 | 不保证，后发先至是可能的 |
| 流控/拥塞控制 | 有（内核实现） | 没有，发多快取决于应用 |
| 头部开销 | 20~60 字节 | 8 字节 |

两个最容易被追问的点：

- **UDP 为什么"快"**：不是代码写得快，而是**没有握手（0 RTT 就能发数据）、没有确认与重传、没有拥塞控制**。开销小、延迟确定，代价是把可靠性问题甩给应用。
- **Datagram 边界**：`Write` 一次 = 线路上一条独立报文 = 对端 `Read` 一次收全。TCP 的粘包问题在 UDP 中天然不存在；但单个数据报最大 64KB（实际受 MTU 影响会分片），且**太大或太快的报文可能被中间设备直接丢弃**。

## 典型使用场景

- DNS 查询：一问一答，报文小，重传逻辑简单（见 Phase 7）
- 视频/语音/游戏：实时性优先，旧数据丢了重传也没意义
- QUIC / KCP：在 UDP 上自建可靠传输——证明"UDP 只是地基，可靠性可以按需造"

## 与 Go API 的对应

```go
conn, _ := net.ListenUDP("udp", addr)   // 绑定端口，无 listen/accept
n, remote, _ := conn.ReadFromUDP(buf)   // 每次读一条完整数据报，并拿到发送方地址
conn.WriteToUDP(data, remote)           // 向指定地址发一条数据报
```

`net.DialUDP` 只是预先绑定了对端地址，之后可用 `Write/Read`，本质相同——UDP 的 "Dial" **不发任何网络包**，没有握手。

## 应用层的可靠性：超时 + 重传

UDP 不负责重传，需要可靠时只能应用自己来：发送后设 deadline 等回复，超时就重发，重发若干次仍失败才放弃。这正是 `udp/retry` 实验做的事，也是 DNS 的做法。

更深一步：如果"可靠 + 有序"全部要，就直接把 TCP/QUIC 拿来用。应用层重传只适合"偶尔丢一两个包可以接受"的场景——重传代价（应用复杂度）远比想象高。
